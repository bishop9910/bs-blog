1: # bs-blog
2: 
3: 一个人的写作空间。前台是手写 CSS 的阅读站点，后台是一个带密码锁的富文本编辑器。
4: 
5: - **前端**：Vue 3 + Vite + TypeScript，根目录
6: - **后端**：Go + Kratos v2 + SQLite（纯 Go 驱动，无需 CGO），`backend/`
7: 
8: 前端与后端通过 `/api/v1` 下的 JSON 通信，字段一律 camelCase。生产环境由 Go 直接托管前端构建产物，**同源部署，因此不需要 CORS**。
9: 
10: ---
11: 
12: ## 快速开始
13: 
14: ### 1. 安装前端依赖
15: 
16: ```sh
17: pnpm install
18: ```
19: 
20: ### 2. 启动后端
21: 
22: ```sh
23: cd backend
24: go run ./cmd/server
25: ```
26: 
27: 第一次启动会自动建库、建表，并在 `backend/data/` 下生成 SQLite 文件与 JWT 密钥。默认监听 `0.0.0.0:8080`，也就是本机用 <http://127.0.0.1:8080> 访问，同一局域网的其他设备用 <http://本机IP:8080> 访问。只想本机可用的话，把 `server.addr` 改回 `127.0.0.1:8080`。
28: 
29: ### 3. 启动前端开发服务器
30: 
31: ```sh
32: pnpm dev
33: ```
34: 
35: 打开 <http://localhost:5173>。Vite 已把 `/api` 与 `/uploads` 代理到 `127.0.0.1:8080`，开发期同样是同源体验。
36: 
37: ### 4. 认领你的站点
38: 
39: 首次打开 `/admin/login` 时，后端还没有任何用户，页面会自动切换到「初始化」模式，让你设置唯一的管理员账号和密码。**这个入口在站点建立第一个用户之后就会永久关闭**（再调用会返回 403），所以不用担心别人抢先注册。

43: ## 生产构建
44: 
45: ```powershell
46: powershell -File backend/scripts/build-release.ps1
47: ```
48: 
49: ```bash
50: bash backend/scripts/build-release.sh
51: ```
52: 
53: 两个脚本做的事完全一样，按平台挑一个：Windows 用 `.ps1`，Linux / macOS 用 `.sh`。一条命令走完：`pnpm build` 产出前端 → 复制进 `backend/internal/web/dist/` → 用 `go:embed` 把前端**编进二进制** → 在 `backend/release/` 下组装交付物：
54: 
55: ```
56: release/
57: ├── bs-blog.exe        前端已内嵌，单个文件即可运行（Linux 上叫 bs-blog）
58: ├── configs/config.yaml
59: └── data/uploads/      图片上传目录
60: ```
61: 
62: 整个目录拷到别的机器就能跑——**不需要 Node，也不需要 dist 目录**，在 `release/` 下执行 `.\bs-blog.exe`（Linux 上是 `./bs-blog`），浏览器开 <http://127.0.0.1:8080>。
63: 
64: | 用途 | `.ps1` | `.sh` |
65: | --- | --- | --- |
66: | 指定版本号 | `-Version 1.2.3` | `-v 1.2.3` |
67: | 跳过前端构建 | `-SkipFrontend` | `-s` |
68: 
69: 版本号默认取 `git describe --tags --always --dirty`，会打进启动日志。
70: 
71: `.sh` 还认 `GOOS` / `GOARCH` 环境变量，所以在 Linux 上交叉编 Windows 版本也是可以的：`GOOS=windows bash backend/scripts/build-release.sh`，产物名会自动变成 `bs-blog.exe`。反过来，在 Linux 上直接跑出来的是一个**静态**二进制（`CGO_ENABLED=0`，SQLite 驱动是纯 Go 的），拷到任何 amd64 Linux 都能直接跑。
72: 
73: **`release/data/` 不会被脚本覆盖。** 数据库是唯一不可再生的东西，脚本只建空目录；如果 `backend/data/blog.db` 存在而 `release/data/` 里没有，它只打一行 NOTE 提醒你手动拷贝，绝不代劳。
74: 
75: ### Windows 图标与版本信息
76: 
77: Windows 产物自带图标和版本元数据（资源管理器里「属性 → 详细信息」能看到），这些资源由 `backend/winres/` 管：
78: 
79: - `winres/icon.ico` 就是 exe 的图标，而且**是个普通的受版本控制的文件**：想换图标就把这个文件替换掉，提交后一直保留，打包脚本不会动它
80: - `winres/versioninfo.json` 是版本元数据（产品名、描述、版权、占位版本号）
81: - [goversioninfo](https://github.com/josephspurrier/goversioninfo) 把这两样编成 `.syso`，Go 再把它链进 exe
82: 
83: `tools/icongen` 只是 `icon.ico` 的**兜底**：万一文件不在（比如新克隆时漏带了），它就用 Go 代码现画一个——圆角底加一个字母 `b`，画在 1024² 的设计空间里再降采样到 16/24/32/48/64/128/256 七个尺寸。它**默认绝不覆盖已存在的文件**，想重画必须显式加 `-force`；打包脚本看到 `icon.ico` 已经在了就连碰都不碰它：
84: 
85: ```sh
86: cd backend
87: go run ./tools/icongen          # 只在 icon.ico 缺失时补一个，有就原样留着
88: go run ./tools/icongen -force   # 重画并覆盖
89: ```
90: 
91: 仓库里预置的 `icon.ico` 是从前端 `public/favicon.ico` 拷过来的，这样 exe 图标和网页标签图标是同一个；换图标时记得两处都换。想用别处的图标，只要是个真 `.ico`（goversioninfo 不吃 `.png`，会报 `bad magic number`）直接覆盖上去即可。
92: 
93: goversioninfo 是**外部工具**，装一次即可：
94: 
95: ```sh
96: go install github.com/josephspurrier/goversioninfo/cmd/goversioninfo@latest
97: ```
98: 
99: 没装也能正常打包，只是产物没有图标和版本标签（脚本会打一行 NOTE 说明）。版本号能解析出 `1.2.3` 时会同时写进资源管理器显示的**数值**版本；解析不出来（比如 `1daaee3-dirty` 这种提交哈希）就只覆盖文本字段，数值保留 `versioninfo.json` 里的占位值。
100: 
101: 交叉编译到非 Windows 目标时这一步自动跳过：`.syso` 只在 Windows 上有意义，而 goversioninfo 生成的 `resource_windows_*.syso` 这个命名本身也保证它们不会被链进 Linux 二进制——即使 `cmd/server/` 里还留着上一次 Windows 构建的残留文件也不会。
102: 
103: 前端是**直接从二进制里读出来**服务的（`internal/web/embed.go`），不做「启动时解压到临时目录」——少一次写盘、少一个清理步骤，也就少一类「临时目录不可写」的启动失败。代价是内嵌文件没有修改时间，所以缓存头是显式写死的：`index.html` 用 `no-cache`（它决定引用哪些带哈希的资源，缓存它等于把浏览器钉在旧构建上），`assets/` 用一年 `immutable`。
104: 
105: 开发时仍然前后端分开跑（见上面的快速开始）。想临时覆盖内嵌前端，把 `server.staticDir` 指向一个目录即可；指向的路径不存在或没有 `index.html` 时会**自动回退到内嵌副本**，所以配错不会把站点打挂。
106: 
107: 要单独手工构建也可以：
108: 
109: ```sh
110: pnpm build                            # 前端产物到 dist/
111: cd backend
112: go build -o bs-blog ./cmd/server      # 从 backend/ 启动时会去读 ../dist
113: ```
114: 
115: 这样编出来的二进制**没有内嵌前端**（只嵌了占位的 `.gitkeep`），启动时会打印一条「serving the API only」的警告；要出页面就得让 `server.staticDir` 指向 `../dist`。

119: ## 测试
120: 
121: 后端带四个端到端测试脚本（Windows PowerShell，不依赖任何外部工具）：
122: 
123: ```powershell
124: powershell -File backend/scripts/smoke.ps1   # 接口：鉴权、文章 CRUD、发布、上传、改密、CORS
125: powershell -File backend/scripts/web.ps1     # 生产托管：SPA 回退、路径穿越防护、目录列表
126: powershell -File backend/scripts/prod.ps1    # 真实整合：用 dist/ 真产物跑通前后端
127: powershell -File backend/scripts/dev.ps1     # 开发回路：vite dev + /api 代理是否接通
128: ```
129: 
130: 它们会在 `.smoke/` / `.smokeweb/` / `.smokeprod/` / `.smokedev/` 下起一次性服务和一次性数据库，跑完自动清理，**不会碰到真实数据**。
131: 
132: 打包用的 `backend/scripts/build-release.ps1`（Linux 上是 `build-release.sh`）不在这四个里面：它们只读前端产物、只写 `backend/release/`，既不碰数据库也不起服务，所以不需要在测试前跑。
133: 
134: 前三个脚本的区别：`smoke.ps1` 只管接口；`web.ps1` 用一个手写的假 `dist/` 验证托管逻辑；`prod.ps1` 用 `pnpm build` 真正产出的 `dist/`，会解析 `index.html` 里引用的每一个资源并逐个请求，能抓到「页面指向了一个 Vite 根本没生成的文件」这类假 `dist/` 永远看不见的问题。**先跑 `pnpm build` 再跑 `prod.ps1`。**
135: 
136: `dev.ps1` 覆盖的是另一条完全独立的代码路径：`vite build` 通过**不能**证明 `vite dev`、代理配置和按需 SFC 编译也没问题。它会同时拉起后端和 Vite，验证 `/api` 代理接通、几个关键 SFC 能被正确编译、且 Vite 没记录任何错误。跑它会占用 5173/8080 端口。
137: 
138: 端口被占用时不会静默通过：`dev.ps1` 会在启动前先探测，发现占用直接报 `port 8080 is already in use -- stop the running dev server first` 并以 1 退出；`smoke.ps1` 可以用 `-Port 8093` 换一个端口，方便和正在运行的开发服务器共存。
139: 
140: 前端用 `pnpm type-check` 做类型检查。
141: 
142: ### 前后端文本契约
143: 
144: slug、字数、阅读时长这三样东西**两边各算一次**：编辑器里算出来给你看，服务端保存时再算一次写进库。两边一旦有分歧，你看到的就是一个 slug，存下去的是另一个。
145: 
146: `scripts/text-cases.json` 是唯一的真值来源，两侧各有一份断言：
147: 
148: ```sh
149: pnpm check:text                                    # 前端 src/utils/text.ts
150: cd backend && go test ./internal/pkg/textutil/     # 后端 internal/pkg/textutil
151: ```
152: 
153: **改任意一边都必须改 `scripts/text-cases.json`**，否则另一边立刻红。`go test ./...` 里唯一有测试的包就是它。
154: 
155: ### 排查库里的真实数据
156: 
157: `backend/cmd/dbdump` 是个只读小工具，用来在没装 SQLite 客户端时看一眼库里到底存了什么——「文章到底没存进去，还是存进去了只是没显示」这类问题一眼可辨：
158: 
159: ```sh
160: cd backend && go run ./cmd/dbdump ../data/blog.db
161: ```
162: 
163: 它以 `mode=ro&_pragma=query_only(true)` 打开文件，**不可能写入**。库跑在 WAL 模式下，所以要看最新的已提交数据，需把 `blog.db`、`blog.db-wal`、`blog.db-shm` 三个文件一起复制出来再读——只复制 `blog.db` 会看到一份陈旧快照。

167: ## 功能
168: 
169: **公开站点**
170: 
171: - 首页：极光 WebGL 背景、统计条、Bento 网格文章流、标签云
172: - 文章列表：分页、按标签筛选、关键字搜索（筛选状态写进 URL，可分享可后退）
173: - 文章详情：阅读进度条、代码高亮、上一篇/下一篇、copy link
174: - 归档：按年/月分组，年份栏吸顶
175: - 标签、关于、404（打字机动画）
176: - 壁纸：后台配好一组之后，**每次打开站点随机挑一张**，电影感的淡入 + 缓慢推镜 + 跟随鼠标与滚动的视差；没有配壁纸时保持原来的极光背景
177: - 音乐：侧边可展开/收起的播放器，左边封面、中间歌词、进度条上方是**正在播放的声音**实时频谱，支持上一首/下一首/顺序/单曲/随机/播放列表，空格键播放暂停，系统媒体键（MediaSession）与手机锁屏也能控制
178: 
179: **管理后台**（`/admin`，需要登录）
180: 
181: - 富文本编辑器：标题/正文、加粗斜体删除线、行内代码、引用、分割线、三种标题、有序无序列表、任务列表、表格、文本对齐、高亮、颜色、链接、图片、撤销重做、字数统计
182: - 图片：拖放或粘贴直接上传，也支持图片库统一管理
183: - 标签：输入即创建，按 slug 去重
184: - 草稿 / 发布：新文章**永远是草稿**，发布是一个单独的动作，半成品不可能误上线
185: - slug：从标题自动派生（中文标题也能生成可读 slug），手动改过之后就不再自动覆盖，实时检测占用
186: - 媒体库、站点信息（标题/介绍/社交链接）、修改密码
187: 
188: **密码锁**
189: 
190: - 单管理员。密码用 bcrypt cost 12 存储，登录换取 HS256 JWT
191: - 改密码会同时递增 token 版本号，让**所有旧 token 立即失效**
192: - 登录失败返回统一提示，不区分「用户不存在」和「密码错误」
193: 
194: **音乐库**
195: 
196: 音乐库就是**一个目录**，没有任何一首歌进数据库——把文件搬进去或搬走，站点播的就是那些文件：
197: 
198: - 递归扫描 `music.dir`（默认 `backend/data/music`），索引 mp3 / flac / m4a / m4b / ogg / opus / wav
199: - 标签与内嵌封面直接读文件（ID3v2 / Vorbis / FLAC / MP4），**时长是纯 Go 解析的**：不需要 ffmpeg，也不需要 CGO
200: - 歌词优先取文件内嵌的，其次取同名 `.lrc`（UTF-8 或 GB18030 都能读，`[offset:]` 会被应用）
201: - 同目录放一个与音频同名的 `.json`（`{title,artist,album,albumArtist,year,cover,lyrics}`）可以覆盖标签，`cover` 是相对音频文件的图片路径
202: - 丢进去之后 `music.watch` 会在 2 秒防抖后自动重扫；也可以在后台「音乐」页点**重新扫描**，或直接拖放上传
203: - 播放走 `GET /api/v1/music/stream/{id}`（支持 Range，拖进度条不会重下整首），封面走 `/api/v1/music/cover/{id}` 并缓存一天
204: 
205: 前端是**同源**取音频的，所以 `AnalyserNode` 能直接读正在播放的声音——进度条上方那排频谱不是随机数，是当前这首歌的实时频率。

246: ## 安全设计
247: 
248: - 富文本在**入库前**用白名单策略净化（Go 侧 bluemonday），前端渲染时再用 DOMPurify 净一次；`javascript:` 之类的 URL 会被丢弃
249: - 数据库里存的是**净化后的 HTML**，公开页因此不需要启动编辑器就能渲染
250: - 文章正文不含 `data:` URI，图片必须走上传流程
251: - 单个请求体、上传体积都有上限；上传目录关闭目录列表
252: - 音频上传做**扩展名白名单 + MIME 嗅探**双校验，落盘名是随机 UUID，原始文件名不会碰到文件系统
253: - 音乐 sidecar（`.json` / `.lrc` / 封面）里的路径必须落在音乐目录内部，`../` 之类的越界引用会被拒绝，不会被当成「读我这个博客服务器上的任意文件」
254: - 壁纸只允许站点相对路径或 http(s) 绝对地址；`javascript:`、`data:`、`//host` 都会被丢掉（前端再按同一套白名单校验一次）
255: - 静态文件回退使用 `path.Clean("/" + path)`，`..` 无法逃出根目录
256: - JWT 密钥首次启动时随机生成并落盘（`backend/data/jwt.secret`），重启不会让所有人掉线。**`auth.secret` 必须留空**：`configs/config.yaml` 是提交进 git 的，密钥写在那里等于公开密钥——任何拿到仓库副本的人都能自己签一个管理员 token，直接绕过密码锁（`data/` 已被 `.gitignore` 排除，生成的密钥不会进仓库）
257: - 首次启动的认领接口 `POST /auth/setup` 在**还没有任何管理员**时对谁开放，谁先访问谁就是站长。`conf.Auth.SetupToken` 是为「认领时需要共享口令」预留的字段，**目前没有任何代码读取它**，所以配置里不放这个键——放一个不生效的值，看起来像一层并不存在的防护
